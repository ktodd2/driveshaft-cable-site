# Referral rewards — staged release review

Prepared from `main` commit `38adb33bbddf38b7625ff3a4df5823ab9aef7d45` (shipping recipient fix, PR 24). All work is local/staged. The migration, feature flags, monthly scheduling, customer emails, and payouts have **not** been enabled in production. The disabled draft is published as PR #25; publishing it did not activate the feature. No historical orders are awarded or backfilled.

## Confirmed rules

- Owner selects past paid customers, enters a custom code or uses Generate code, and assigns a unique code and explicitly reviews/sends each invitation. No public enrollment, login, credentials, or referrer dashboard.
- Invitation signup asks for full name, mailing address, preferred check/product reward and acceptance of the displayed rules. The invited email is fixed. A random 256-bit token is stored only as SHA-256, expires after seven days, and is consumed once. A synchronous script removes the token fragment before analytics. Signup returns only that referrer’s code and name.
- New buyers must enter a valid active code on their first-ever paid order. No retroactive attribution or self-referrals. Exact trimmed, lowercased email is permanent identity; dots and plus tags remain distinct. Changing email creates a different identity; no automatic merging.
- Each referred buyer has their own sequence: order 1 = 10%, 2 = 5%, 3–10 = 2%, 11 onward = 1%. Rates and sequence are stored once. Fully refunded orders keep their position and do not re-tier later orders.
- Commission uses server-priced merchandise after all existing discounts. Shipping and tax never earn commission. Existing loyalty pricing and discount precedence remain intact; entering a referral code adds no discount.
- Only new website retail Stripe payments with a server-created snapshot qualify. Manual, wholesale, test-mode, synthetic, abandoned, failed and pre-rollout payments do not create rewards. A canceled-before-payment intent is refused.
- Seven days from verified Stripe success. For an out-of-order refund delivered before success, eligibility initially uses the later observation time, then is corrected by the signed success event. Charge creation time is not used as an asynchronous payment’s success time.
- Monthly queue on the 1st in **America/Chicago**, no minimum. Monthly statements show balances and ask the referrer to reply with check or products. After an approved rollout, the monthly worker automatically prepares and emails one frozen statement per eligible partner/month. Signup and activation cutovers choose the first Chicago month boundary on or after enrollment/launch. Owner approval remains required for payouts, not for each statement email. No real scheduler was created.
- Every redemption requires owner approval. Check issuance is recorded manually with a reference; no bank/check provider is connected. Product requests debit retail merchandise value **plus shipping**, and any tax amount the owner separately determines. No automatic tax or discount-stacking assumption. Insufficient balance blocks approval and completion.
- Refunds reduce future earnings even after issuance; balances may be negative. Partial refunds hold the affected reward until the owner identifies cumulative refunded merchandise after discounts. A shipping-only refund can have zero merchandise reduction. Full refunds automatically reverse the entire commission. Open/lost disputes hold the affected reward; a verified won/closed-warning dispute releases it. Issued rewards remain in history.
- Monthly statements include only that referrer’s attributed customer names, eligible product spending and commissions. The purchase-period month (the previous Chicago calendar month) and lifetime totals are separate. Mixed rates are shown per order/rate group; refund reductions and pending/vested/held timing are explicit. Unallocated partial refunds are excluded from confirmed net spend/commission and shown as provisional upper bounds. Overall available rewards deduct payouts/reservations; per-customer vested totals are before those account-level deductions. Buyer emails, addresses, tax, shipping and payment references are excluded. The buyer sees a disclosure beside code entry covering this and future orders under the same email.
- Custom codes trim/uppercase case-insensitively and accept 3–24 letters, numbers or internal hyphens. Generated `DC-` codes use eight random characters without I/O/0/1. Database uniqueness is atomic; a generated collision retries up to eight times, while a custom collision receives a clear error. Codes are not authentication secrets. This draft provides no existing-code edit API, so neither another owner’s code nor permanent attribution can be overwritten.
- No tax-form collection feature. This is not a determination of reporting obligations.

## Architecture and flow

1. Checkout creates its existing order and sends a tab-private capability. The server recomputes prices/discounts/shipping/tax, validates retail eligibility and the referral code, then creates an immutable `referral_checkouts` snapshot. Only a SHA-256 capability hash reaches storage/Stripe. Repeating a lost request in the same checkout reuses its order and provider idempotency key; a different capability, code, amount, address or cart cannot recover it.
2. Concurrent checkouts proceed normally. No payment is canceled and there is no per-email checkout limit. Each order has its own private capability and provider idempotency key. An unknown response for that same order beyond 23 hours requires owner/provider review rather than recreating an uncertain charge; starting a different checkout remains possible. The earlier proposal to serialize/cancel checkouts was removed before release.
3. After legacy fulfillment, the signed webhook retrieves current PaymentIntent/charge/dispute records directly from Stripe and records payment/refund observations. It checks other unsettled intents for that email. An earlier unverified success or uncertain intent holds rewards, never checkout. Once authoritative success timing and prior unpaid observations establish order, a transactional email lock binds the true first referrer and assigns immutable tiers in payment-time order (same-second known successes use source order ID as a deterministic tie-break). Refunds are stored even before tier allocation. Replays, stale refunds and failed-after-success events cannot duplicate earnings. No sequence is guessed from webhook arrival order.
4. Private tables hold partners, hashed invitations, checkouts with immutable buyer-name capture (including missing names), buyers, earnings, redemptions, monthly statement snapshots and an audit trail. All have RLS enabled. All table and function access is revoked from PUBLIC, anon and authenticated; only service-role access is granted. Functions are SECURITY INVOKER. The admin Edge endpoint validates the user with `auth.getUser` and the current active `admin_users` row, then passes that verified actor to SQL for a second check.
5. Partner-row locks serialize credits, refunds, maturity corrections, approvals and issuance. Requested → reserved → paid; reject releases a reservation. Double approvals/completions are idempotent. Completion rechecks balances after refunds. The admin UI exposes per-code counts, per-email/order sequence and rate, and pending/available/held/reserved/paid/reversed balances.
6. Existing `email_attempts` and `createEmailRecorder` claim/dedupe infrastructure is reused for invitation and monthly email sends. Manual and automatic statement paths share the exact automation/entity/template identity and frozen recipient/body. A two-minute worker lease, 50-message/40-second cap, 600ms spacing, and a durable unclaimed queue support safe repeated invocations. Claimed/held rows are filtered before the batch limit. Current-month preparation can catch a missed 1st; frozen unsent prior-month statements remain queued. Missing historical months are not newly backfilled or backdated. The email states the actual balance-preparation time. Cumulative provider-review counts stay visible across later empty runs. Unknown provider outcomes are held for verification; never blindly retried. Only invitation hashes are retained, so a failed/uncertain invitation requires delivery review and expiry before a fresh link. No signup email is automatically sent by adding a partner. Statement customer details are frozen with the balance; no live name/email lookup is used at send time. Plaintext names are bounded, controls/Bidi are removed and email-like name tokens are redacted.

## Review decisions and existing gaps

- **Partial refunds:** Stripe’s aggregate refunded cents do not identify merchandise versus shipping/tax. The implementation holds that earning for owner allocation, with bounds checked against the original components. This avoids inventing product revenue. Review this operational step before launch.
- **Reward reconciliation:** no new checkout restrictions or payment cancellations remain. Uncertain payment timing holds rewards, and the admin UI shows unresolved source orders. Missing signed success events require provider replay/verification before earnings can settle. Reconciliation scans at most 100 unsettled snapshots per email; larger sets hold rewards for review. Lost-response retry works in the current tab with the private capability; a tab refresh can start a separate checkout without canceling the earlier one. Payment cancellation is never an automatic referral action.
- **Monthly emails:** automatic delivery is implemented and tested locally, disabled by default. A recurring hourly scheduler is a required release configuration; a once-monthly invocation would not drain more than one bounded batch. The hourly worker sends only each due monthly statement once, then skips accepted/held claims. Uncertain or rejected deliveries require provider review; they are not blindly retried. Every payout remains manually approved.
- **Existing live order exposure is a release blocker:** read-only schema inspection found `Allow reading own orders` permitting anon SELECT with `true`, `Allow anonymous payment status updates` permitting anon UPDATE with `true`, and authenticated order policies using `true`. The new reward ledger does not trust those mutable payment flags for earning, but the existing order table exposes buyer information. No production access changes were made. A separate reviewed migration and server-owned checkout/order APIs are needed to remove that exposure while preserving checkout/admin/tracking behavior.
- Existing Stripe Tax refund reversal remains an unrelated TODO in the legacy webhook. Referral adjustments do not modify tax filings or shipping costs.
- The existing Stripe SDK/API version is retained to avoid an unrelated payments upgrade. Current webhook signature guidance was checked against [Stripe documentation](https://docs.stripe.com/webhooks). Supabase RLS guidance and the current changelog were consulted; no applicable database API breaking change was required.

## Rollback and operational recovery

- Disable the frontend code field, set `referral_settings.enabled=false` to stop new enrollment/code use, turn email and automatic-statement flags off and stop the new statement-check job. Do not touch existing schedules. Once any permanent link exists, keep `REFERRAL_REWARDS_ENABLED=true` and the server snapshot/reconciliation integration deployed so future retail orders for linked emails still earn; the database enrollment flag does not block their checkout or accrual. Turning off server tracking after launch would lose future commissions and is not a safe routine rollback.
- **Keep the new webhook reconciliation and private ledger in place** for previously prepared/paid snapshots, refunds and disputes. Do not drop tables or revert to a webhook that ignores outstanding liabilities. Disabling enrollment does not erase permanent attribution or earned balances.
- Stop approvals/sends during a discrepancy. Export and reconcile by source order/intent IDs and immutable tier before resuming. Recorded check/product issuance is manual and cannot be undone with a software rollback.
- Unknown payment response older than 23 hours: verify the original provider idempotency request and order metadata in Stripe, record the exact intent ID and replay the signed success event if needed. Never blindly recreate the same uncertain charge. This holds only that recovery/its uncertain rewards; it does not block a different checkout or cancel a payment. There is no force-unlock or automatic cancellation action.
- Unknown email outcome: verify provider acceptance in the existing email history/Resend before changing an invitation or retrying. A used or expired invitation cannot enroll twice. Do not log or save raw invitation links in support notes.
