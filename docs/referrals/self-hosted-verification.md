## Flow and safeguards

1. Buyer enters an email and explicitly completes the bundled widget's browser check. The widget uses Web Workers with a 90-second timeout and no interaction fingerprinting. Changing email/request or leaving the component cancels its fetch/work. The mail button remains disabled without a solved challenge. Load/work errors have no bypass; the buyer can retry or contact the owner.
2. A POST issues a signed five-minute challenge, bound to normalized email hash, UUID, action, exact Supabase project and fixed invitation origin. No email is put in a URL or worker challenge. The signature key is derived inside the server with HMAC-SHA-256 from the existing modern backend key, separated by purpose/project/origin. Raw backend key and derived signing material never leave the server. Rotating that existing key invalidates outstanding browser challenges; it does not alter already emailed links or receiver proofs.
3. Issuance is stateless, bounded by the public endpoint's body/time limits and server feature/configuration checks, and performs no database operation or shared quota claim. The separate reviewer found that the proposed global pre-work counter let 30 unsolved requests lock out unrelated buyers. That unshipped migration/call was removed. A public challenge grants no email, ownership, reservation or send-budget slot. Request/send still fails closed if DB settings are disabled/unavailable; valid work is verified before reading those settings.
4. Server fixes PBKDF2/SHA-256, cost 5,000, 32-byte output and prefix `00`, and bounds payload, fields, nonce/salt, time and counter before validating the signature and actual solution through the library. It does not accept arbitrary client-supplied algorithms/costs. The existing SQL mail claim consumes the **signed challenge identity**, not its encoding or solution; reordering JSON, changing timing metadata or solving it another way cannot obtain another email.
5. Existing mail limits remain: one-minute email cooldown, three/email/hour, 25 global/hour, 100/day, 1,000/UTC month. Durable send claims and uncertain-outcome holds remain. Challenge issuance creates no checkout reservation, account, email ownership or proof.
6. The receiver still explicitly consumes the one-hour private email link with independently generated browser proof. Strict first-paid coordination, capabilities, cancellation rules, permanent attribution, discount stacking, immutable prepared/earned terms, commission schedules, refund accounting and owner payout approval are unchanged.

## What differs and remains unverified

Proof of work adds computational expense to automation; it does **not** attest that a visitor is human and does not provide Cloudflare's adaptive classification. A determined attacker can solve challenges and exhaust the deliberately conservative global limits, causing legitimate new buyers to wait or contact the owner. Lower-powered/unsupported browsers can take longer or fail closed. Desktop and mobile-viewport browser solving pass locally; real lower-powered mobile-device performance remains unmeasured. There is no silent less-protected fallback.

Unit/integration/browser fixture source has been updated for the new protocol, including signature/identity/expiry/tamper checks, replay identity, stateless issuance/no-DB abuse checks, database authorization, real offline worker solving and existing ownership/checkout behavior. Current local execution results and exact limits are recorded in [the validation report](self-hosted-validation.md); they are not provider delivery or production readiness evidence.
