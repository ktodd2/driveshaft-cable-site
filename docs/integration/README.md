# Secure checkout and referral composition — local only

This branch composes main-based access repair `020cec1` with referral rewards `d074e96` and follow-up `29ed34e`. Both original branches remain separate. Draft GitHub publication was separately approved on 2026-11-03. This branch has not been deployed or applied to a hosted database. No real payment, order, invitation, statement, schedule or payout was created.

Independent read-only review found no additional payment-capability, admin-authorization or PII bypass. It identified Unicode-name retry and ambiguous legacy-payment ordering issues; both received targeted fixture coverage and conservative fixes.

The private secure checkout is the sole source of order identity, frozen pricing and Stripe parameters. Before its one provider creation, `prepareSecureReferral` calls the service-only named wrapper with the same order UUID, email, canonical frozen name, product revenue after discounts, shipping, tax and exact immutable parameters. The only provider key is `secure-checkout/<request UUID>`. The entered referral code is separate from discounts and part of the private request fingerprint. Metadata is stamped only when the server rollout flag is enabled. Disabled rollout refuses entered-code promises before creating a payment; ordinary uncoded checkout still works.

After secure intent association, the matching referral snapshot is associated with that same intent. Observed/paid retries preserve their existing identity. Prepared snapshots survive paused enrollment. Missing names stay captured as missing; Unicode whitespace uses the same canonical representation for storage and retry verification. If an untracked legacy order becomes paid during referral checkout, payment-time history cannot be reconstructed from public order timestamps. A separate composition migration leaves code-bearing ambiguous cases observed for owner review instead of permanently nulling a potentially rightful referrer; it does not award historical commissions. Ordinary uncoded historical repeats settle without rewards or unnecessary review holds. Resolve such cases with verified provider evidence under a separately reviewed procedure, never by guessing or deleting history.

Neither enrollment nor reconciliation blocks or cancels ordinary concurrent customer checkouts. The signed webhook first reconciles authoritative payment, stock and discount effects, then runs reward payment/refund/dispute reconciliation; reward failures remain retryable. Confirmation keeps server-owned fulfillment and waits for signed delivery before awarding rewards.

## Release gates and order

Draft publication of this integration/access diff is approved; keep both drafts unmerged. Hosted staging and production operations remain unapproved. Before any launch, obtain explicit staging authorization and run gateway authentication/RLS/advisor checks, actual multi-connection concurrency, intercepted statement delivery, Stripe test-mode raw webhook/return/retry/refund/dispute/tax checks and admin manual/order/shipping/report regressions in an isolated project. Local serialized PGlite is not hosted concurrency or provider-delivery certification.

Do not blindly apply the whole chronological chain while old frontend tabs can still create public orders. Invites/statements remain provider-gated and idempotent, and all check/product redemptions still require owner approval. Keep the secure service schema/receipts on rollback, retain compatible server reconciliation, and never restore permissive anonymous order access as a routine rollback.
